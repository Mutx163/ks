**日期**: 2026-06-14  
**审查人**: MiMo (AI 代码审查)  
**审查范围**: 全项目代码审查（前端 JS/HTML/CSS + Cloudflare Worker 后端 + Vite 构建配置）  
**目标**: 发现影响"最新数据正确性"和"最快加载速度"的 Bug

## 🔴 确认存在的 Bug

### 1. `pushStats` 失败时排行榜数据永久丢失

**文件**: `js/quiz-nav.js`（3处）+ `js/api.js`

**问题**: `_lastPushAnswered`、`_lastPushCorrect`、`_lastPushDuration` 在网络请求**发出前**就被更新了。如果请求失败（网络断开、超时等），本次的 delta 永远无法重发。

```js
// quiz-nav.js - _flushStatsNow()
state._lastPushAnswered = submittedIds.length;  // ← 先更新了
state._lastPushCorrect = correctCount;
state._lastPushDuration = duration;

return API.pushStats({  // ← 然后才发请求，失败了 delta 就丢了
    answered: dAnswered,
    correct: dCorrect,
    duration: dDuration
});
```

**复现场景**:
1. 用户答了 10 题，对 7 题 → `_flushStatsNow` 发出 delta(10, 7) → **网络失败**
2. `_lastPushAnswered` 已经变成 10
3. 用户再答 5 题 → `_flushStatsNow` 发出 delta(5, x)
4. 排行榜最终只记录了 5 题，而不是 15 题

**同样的模式存在于**: `_saveAndTrackStats()` 和 `renderResult()` 中，共 3 处。

**修复方向**: 只在请求成功后才更新 `_lastPush*`，或者失败时回滚计数器。

### 2. CDN 缓存被 `_ts` 参数完全废掉 — Worker 的 `max-age=300` 形同虚设

**文件**: `js/api.js` 第 86-87 行 + `worker/src/index.js` `handleGetBank()`

**问题**: Worker 为单个题库设置了 5 分钟 CDN 缓存:
```js
// worker - handleGetBank()
return json({ ok: true, bank: {...} }, 200, origin, 300);  // Cache-Control: max-age=300
```

但前端 **每次 GET 请求都加 `_ts=时间戳`**:
```js
// api.js - request()
if (method === 'GET' && options.cacheBust !== false) {
    urlObj.searchParams.set('_ts', Date.now().toString());
}
```

每次 URL 不同 → Cloudflare CDN 认为是不同请求 → **永远不命中缓存** → 每次都打到 D1 数据库。

**影响**:
- 每次打开网站都查询 D1（增加 ~100-300ms 延迟）
- D1 读操作白白消耗
- Worker 设置的 `max-age=300` 是死代码

### 3. 页面间无任何题库数据缓存 — 每次打开 quiz.html 都重新加载

**文件**: `js/storage.js` + `js/quiz-core.js`

**问题**: 题库数据 **只存在内存中**（`Storage._bankData = new Map()`），不持久化到 localStorage 或 sessionStorage。

```js
// storage.js
const Storage = {
    _bankData: new Map(),  // ← 纯内存，页面关闭即丢失
    // ...
};
```

**流程**:
1. 首页 `index.html` → 加载全部题库（1 + N 次 API 请求）→ 存入内存
2. 用户点击题库 → 跳转 `quiz.html`（**新页面**）
3. `quiz.html` 的 `Storage._bankData` 是空的 → 重新请求该题库
4. 用户返回首页 → 再次加载全部题库

**影响**:
- 每次刷题开始前多 1 次 API 请求（~200-500ms）
- 每次返回首页多 N 次 API 请求
- 中国网络环境下体感更明显

### 4. 多页面并行 `autoSync()` 可能导致 `pushProgress` 被吞

**文件**: `js/api.js` + `js/app.js` + `js/leaderboard.js` + `js/insights.js`

**问题**: `pushProgress()` 使用 `this._syncTimer` 做 5 秒防抖，每次调用会 `clearTimeout(this._syncTimer)` 取消前一个。

虽然不同页面各自有独立的 `API` 实例（不同 JS 上下文），但在**同一页面内**，`autoSync()` 和 `saveSession()` 都调用 `pushProgress()`：

```js
// autoSync → pushAll → pushProgress (debounce 5s)
// 用户答题 → saveSession → pushProgress (debounce 5s, 取消了上面的)
```

**影响**: 低严重度。数据不会丢，但有冗余网络请求。

---

### 5. 题库 `questions_json` 损坏时静默返回空数组

**文件**: `worker/src/index.js` `handleGetBank()`

```js
let questions = [];
try { questions = JSON.parse(bank.questions_json || '[]'); } catch {}
// ← catch 里什么都没做，questions 保持 []
```

**影响**: 如果管理员导入了损坏的 JSON，API 返回 `ok: true` 但 `questions: []`。用户看到的是一个「0 题」的题库，没有任何错误提示。

### 6. `loadAllBanks` 全部失败时无 localStorage 降级

**文件**: `js/bankLoader.js` + `js/app.js`

题库列表加载失败 → 首页显示"网络连接失败" → 用户体验差。

**建议**: 缓存上次成功的题库列表到 localStorage 作为降级方案。

---

### 7. `_mergeProgress` 中 `duration` 取最大值导致多设备时长统计偏低

**文件**: `js/api.js` `_mergeProgress()`

```js
if (cloudDuration > localDuration) {
    l.duration = cloudDuration;
}
```

**场景**:
- 设备 A 学了 100 秒，设备 B 学了 80 秒（同时使用）
- 合并后: `max(100, 80) = 100`（实际应该是 180 秒）

**影响**: 多设备同时使用时，学习时长统计偏低。

## 🟡 性能优化问题（非 Bug，但影响速度）

### 8. 外部 CDN 资源无备选方案，在中国可能加载缓慢

**文件**: `index.html` / `quiz.html`

加载了 4 个外部 CDN 的 10+ 个资源：
- `cdn.jsdelivr.net`（Lucide 图标、KaTeX 数学公式）— 在中国访问时快时慢
- `cdn.bootcdn.net`（Prism.js 代码高亮、Marked.js）— 相对稳定

**没有 fallback 机制**。如果 `cdn.jsdelivr.net` 卡住，图标和数学公式就无法显示。

**建议**: 考虑将这些资源打包到 Vite 构建中，或使用 unpkg/cdnjs 等替代源。

---

### 9. HTML 文件无显式缓存策略

**文件**: 所有 `.html` 文件

Vite 生成的 JS/CSS 有 hash（如 `index-CHLLR2cg.js`），但 HTML 文件名不变。Cloudflare Pages 默认会对 HTML 做边缘缓存 + 后台重新验证（stale-while-revalidate）。

**建议**: 添加 `_headers` 文件显式控制缓存策略。

---

### 10. 首页加载时同时发起大量并发请求

**文件**: `js/app.js` `init()`

页面加载时同时启动：
1. `BankLoader.loadAllBanks()` → 1 + N 个 API 请求（并行）
2. `API.autoSync()` → 2-3 个 API 请求（pull + push）
3. `renderCustomStats()` → 1 个排行榜 API 请求
4. `loadAnnouncement()` → 1 个公告 API 请求

总计可能 10+ 个并发请求。在中国移动网络下会导致请求排队等待，增加延迟。

## 📊 总结

| 编号 | 问题 | 严重度 | 影响 |
|------|------|--------|------|
| 1 | `pushStats` 失败时 delta 永久丢失 | 🔴 高 | 排行榜数据不准 |
| 2 | CDN 缓存被 `_ts` 废掉 | 🔴 高 | 每次都查 D1，慢且费资源 |
| 3 | 题库数据无跨页面缓存 | 🔴 中 | 每次跳转都重新加载 |
| 4 | `pushProgress` 防抖可能吞请求 | 🟡 低 | 偶尔冗余请求 |
| 5 | 损坏题库静默返回空 | 🟡 中 | 用户无感知的数据丢失 |
| 6 | 题库加载无 localStorage 降级 | 🟡 中 | 离线/弱网体验差 |
| 7 | 多设备时长取 max 而非 sum | 🟡 低 | 时长统计偏低 |
| 8 | 外部 CDN 无 fallback | 🟡 中 | 中国用户体验不稳定 |
| 9 | HTML 无显式缓存策略 | 🟢 低 | 影响小 |
| 10 | 首页并发请求过多 | 🟡 中 | 弱网下加载慢 |

**最关键的是 #1 和 #2** — #1 是数据正确性 bug，#2 是性能瓶颈（对"最快加载速度"目标影响最大）。
