## R1 · 止血批（F-5 / F-1 / F-3）

### A1.1 F-5 收藏按钮 + 收藏模式（核心）
1. 本地 `npm run dev` + `wrangler dev --local`，注册测试账号，进 `quiz.html?bank=smoke-c&mode=all`
2. 点 `.btn-bookmark` → 断言 `document.querySelector('.btn-bookmark').classList.contains('active') === true`
3. 刷新/切题往返后再断言一次（持久化后仍 active）
4. 进入 `quiz.html?bank=smoke-c&mode=bookmark` → 断言加载题数 `> 0` 且等于已收藏数，且**不出现**「没有收藏的题目」提示、**不跳回** `index.html`

**PASS**：4 条全真；**FAIL**：按钮无 `active` 或收藏模式 0 题（当前基线即 FAIL，`.tmp-test/probe.mjs` 已复现 `cls="btn-bookmark "`）

### A1.2 F-1 主题跨设备同步
1. 设备 A 切深色 → 触发同步（`API.pushSettings`）→ `GET /api/cloud-data/:didA` 断言 `settings.theme === 'dark'`
2. A 清空 localStorage 重载 → 断言 `data-theme === 'dark'`
3. 新 profile（设备 B）绑定同一同步码 → 拉取后断言 `data-theme === 'dark'`

**PASS**：三处都是 dark；**FAIL**：任一处回退到 `auto/light`

### A1.3 F-3 队列残留止血
1. 构造 `dAnswered ≤ 0 && dCorrect > 0` 的请求（清空错题本链路，或直接 `POST /api/sync` 带该增量）
2. 断言响应 **200**（不再是 400），若后端加了标记则 `clamped === true`
3. 触发 `flushSyncQueue()` → 断言 `ks_sync_queue` 中该 bankId 条目被清空（`SyncQueue.isEmpty() === true`）
4. 回归：正常增量（answered>0, correct≤answered）仍累加正确

**PASS**：200 + 队列清空 + 正常增量不回归

## R2 · 安全批（B-1 / B-2 / B-3）

### A2.1 B-1 同步码限流
1. 对 `POST /api/bind` 用**不存在**的同步码同 IP 连打 10 次 → 断言出现 **429**（或失败计数阈值后的锁定响应），且日志/表里能看到失败计数
2. 用已知同步码再试 → 断言仍 200（限流不误伤正常绑定）

**PASS**：N 次后 429 + 正常码 200；**FAIL**：10 次全是 404 无限尝试（当前基线）

### A2.2 B-2 管理员登录限流
1. 用 5 个不同随机 deviceId + 错误密码连打 10 次 → 断言仍被拒（429/冷却提示），不是每次都能继续试
2. 冷却期内用**正确**密码 → 断言被拒或提示冷却；冷却后恢复正常

**PASS**：换 deviceId 无法绕过；**FAIL**：换 id 即可无限试（当前基线）

### A2.3 B-3 AI 接口收口
1. 无 `deviceId` 的 `POST /api/ai/explain` → 断言 401/429（被拒），不产生上游调用
2. 已注册 deviceId 在配额内 → 断言 200 且流式返回
3. 超配额 → 断言 429

**PASS**：无凭据被拒 + 配额内可用；**FAIL**：无凭据也能触发（当前基线）

## R5 · 数据可信度批（roundId / F-2 / 脏数据）

### A5.1 roundId 幂等
1. 同一 `roundId` + 同一增量连发 2 次 → 断言 `stats.answered` 只增加 1 次
2. 不同 `roundId` → 断言正常累加
3. **不带** `roundId`（老客户端）→ 断言行为与当前完全一致（累加）

**PASS**：三例全对；**FAIL**：同 roundId 翻倍

### A5.2 F-2 重开不重复累计
1. 记录云端 `stats.answered` 基线
2. 完成一轮 →「重新开始」→ 再完成同批
3. 断言云端增量 = 本轮实际作答数（不是 2 倍）；排行榜同账号数值与云端一致

### A5.3 脏数据处理
断言存在**书面决策**（D3 的 A/B/C 之一）；若选人工校正，给出 per-user/bank 校正前后报表 diff，并抽 3 个用户人工核对；若选接受/标记，页面或文档有对应说明

### A5.4 排行榜回归
发布前后取排行榜前 10 名（`/api/leaderboard?limit=10`）对比：只允许出现「被修正的用户」变化，其余账号数值不得漂移

## 无法验证的假设（必须在路线图中标注，不能当事实用）

| # | 假设 | 为什么无法验证 | 解封方式 |
| --- | --- | --- | --- |
| U1 | 生产 `users.bookmarks` / `is_admin` 是否存在 | wrangler 未登录、无 `CLOUDFLARE_API_TOKEN`；公开 GET 不触发这两列 | 用户给 token 或本地 `wrangler login` 后跑只读 PRAGMA（E-2/R0） |
| U2 | 生产迁移实际执行到哪一步 | `migrations/` 无 0001、无迁移状态表，代码判断不了 | 同上，`PRAGMA table_info` 反推 |
| U3 | 已落库的排行榜脏数据规模 | 只读接口无法区分「正常累加」与「重复累加」，没有增量历史 | R5 第一个动作导出 per-user/bank 报表 + 人工抽核 |
| U4 | 线上受影响用户比例（收藏/主题） | 无埋点、无错误日志可归因 | 加临时统计或按用户反馈抽样 |
| U5 | 生产 D1 体积 / 距 2MB 行上限的余量 | 无凭证、无只读统计接口 | 拿到凭证后 `SELECT length(questions_json)` 只读查询 |
| U6 | Q-1 的 23 道空答案是否为产品有意 | 产品对简答题「自评」的预期未书面化 | 用户/出题人确认；不阻塞其他批 |
| U7 | R4 图片导入端到端（含 admin UI 上传解析） | 本阶段禁写 D1，未做真实导入 | R4 第一个动作在本地 admin 端到端导入一次 |

> U1 若被证实（缺列），R0 置顶，`/api/bookmarks` 全网 500 属 P0 级；U2–U5 只影响"要不要现在做"，不影响「做了要验收什么」。
> R4/Q-3 的依赖事实**已有报告内证据**：线上 75 vs 本地 87（`GET /api/bank/fixture-design-ch2` 200）、img 题 12 道 id 76–87、12 张图 12/12 存在且已进 dist、导入链路原样保存 questions_json、公开接口不过滤 img、渲染器有 img 分支——唯一缺的是端到端动态验证（U7）。

## 验收结论口径

- 每批验收由我出「PASS/FAIL + 证据路径（JSON/截图/命令输出）」，FAIL 必须带复现步骤
- 涉及生产写操作的批次（R4/R5/R0），验收分两段：**本地预演 PASS** 才允许排生产窗口；生产执行后再做**只读复核**（GET 断言 + 排行榜回归）
- 发布与回滚成本以 `docs/release-impact-*.md`（发布官产出）为准，本文只负责「怎么判过」
