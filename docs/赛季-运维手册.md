## 2. 赛季切换怎么用

三个管理端点（都需要管理员鉴权：`X-Admin-Password` + `X-Admin-Device-Id`，且该 device 映射的用户 `is_admin=1`）：

- `GET /api/admin/seasons`：列出全部赛季
- `POST /api/admin/seasons`：新建赛季（id 手工指定，正则 `[a-z0-9][a-z0-9-]{1,31}`）
- `POST /api/admin/seasons/:id/activate`：把某个赛季设为当前赛季

规则：
- 全表**至多一个** `is_active=1`（靠部分唯一索引 `idx_seasons_active` 保证，不是靠代码自觉）
- 切换后**缓存 30 秒**生效，不是瞬时；刚切完看到旧榜单属正常
- 切换**不会**清空任何数据：旧赛季成绩原样留在那个赛季下，可随时切回去查
- 学生端 localStorage 的进度、错题本、收藏**不随赛季重置**，重置的只有排行榜与统计

## 3. 回滚真相（最重要的一节）

**0007 已经 `DROP TABLE stats` 重建，单靠 `wrangler rollback` 回滚代码不会恢复表结构。**

| 想回退什么 | 正确做法 | 代价 |
| --- | --- | --- |
| 只回代码（接口逻辑错） | `wrangler rollback -c worker/wrangler.toml` 回 `ff354b45` | 低。但代码会按旧 schema 读 `stats`，若旧代码不认 `season_id`，排行榜可能异常 |
| 回结构（表结构不对） | 只能**整库恢复**快照：`wrangler d1 import` 或按导出 SQL 重建 | **高**：会覆盖快照之后的所有写入（新赛季成绩、新用户、日志全部回到 2026-11-16 23:00 前） |
| 只回某个赛季的数据 | 手工 SQL 修正 | 高，且必须先把相关行导出留档 |

结论：**想清楚再动。** 回滚代码 ≠ 回滚数据；回滚数据 = 回到快照时刻。

## 4. 历史赛季为什么写不进去

- 写入时**服务端自己解析当前赛季**（`is_active=1` 那条），**完全忽略**客户端传上来的 `season` 参数
- 所以客户端传 `season:'legacy'` 不会 400，而是被静默忽略、数据落到当前赛季
- 这样老客户端（不带 season）和新客户端行为一致，也不会因为传错而报错
- 历史赛季没有任何写入口：前端不给按钮，服务端不接受

## 5. 迁移注意（下次再动 schema 时）

- 本仓库迁移链：`0001` 基线 → `0002/0003/0004` → `0005` 限流表 → `0006` 赛季表 → `0007` stats 重建
- `0001` 全部 `IF NOT EXISTS`，在生产补记录时是空转；但**它仍然是一次生产写**，执行前照样要快照
- `0007` **不是幂等的**，重放会把 stats 再拆一遍并丢数据；本地请用 `scripts/apply-migrations.ps1`（对 `stats_season` 有 PRAGMA 守卫）
- `wrangler d1 export` 期间数据库会短暂不可用（本次约几十秒），挑低峰做
- 每次 `apply` 前先 `SELECT id,name FROM d1_migrations ORDER BY name` 核对已有记录

## 7. 清理测试账号的正确顺序（外键依赖）

`users` 是父表，`devices` 与 `stats` 是子表，**都必须先删子表再删父表**，否则报 `FOREIGN KEY constraint failed`：

```sql
-- 1) 子表：统计（按赛季）
DELETE FROM stats WHERE user_id IN ('<uid1>','<uid2>');
-- 2) 子表：设备
DELETE FROM devices WHERE user_id IN ('<uid1>','<uid2>');
-- 3) 父表：用户
DELETE FROM users WHERE id IN ('<uid1>','<uid2>');
```

**教训**：第一次查 `devices` 时得到空结果，就直接下了「没有设备行」的结论，实际上有 2 行——那次是查询输出解析偶发失败，不是数据为空。**凡是「查到 0 行」且要据此做删除或判断依赖时，必须换第二种方式复核**（`SELECT COUNT(*)`、按 `user_id` 反查、或再跑一次），别只信一次输出。
