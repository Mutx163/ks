## 0. 结论

1. **发布链路有两条，成本不对称**：前端改 `git push origin main` 即由 Cloudflare Pages 自动构建上线（约 1-2 分钟）；Worker 只能手工 `wrangler deploy`，**无 CI 自动化**。
2. **Worker 发布当前被卡死**：`wrangler whoami` → `Not logged in. Your auth token has expired... non-interactive... set CLOUDFLARE_API_TOKEN`。因此涉及 `worker/` 的第 2、3、5 批**现在发不出去**，第 1 批的后端 3 行 clamp 同理。恢复凭证是路线图的发布前置条件。
3. **D1 是不可逆的一档**：`schema.sql` 与 `/api/*` 的写操作都无法随代码回滚；迁移只能靠 `d1 export` 备份 + 反向 write-down 迁移。
4. **CI 与线上部署解耦**：`.github/workflows/ci.yml` 只在 push 后跑 lint/build 并上传 artifact，**不拦 Pages 部署**；「CI 绿」不能作为可发布证据，发布前必须本地实跑 lint/build。
5. **最危险的回滚缺口在题库批**：导入接口只增不减（`index.js:1997/2015` 追加 `maxId+1`），`bank_history.snapshot` 是死字段（从未写入），题目一旦进生产库**没有通过管理后台撤回的路径**。

## 1. 逐条评估

### 建议 1｜止血批（F-5 收藏、F-1 主题、F-2/F-3 同步语义）

| 项 | 评估 |
| --- | --- |
| 发布方式 | 两条链路混合：`js/` 改动走 Pages 自动部署；`index.js:765-767` 的 3 行 clamp 走 `wrangler deploy` |
| 影响面 | 全站前端（所有页面共用 `api.js`/`storage.js`）；clamp 影响 `/api/sync` 全量调用方 |
| 回滚成本 | **低**（仅前端部分）：Pages 控制台回滚到上一部署，或 `git revert` + push，1-2 分钟。Worker 部分回滚需 `wrangler rollback`（同样被凭证卡住） |
| 停机 | 否。Workers 版本切换原子完成；Pages 回滚瞬时 |
| 数据迁移 | **否**。clamp 只改校验逻辑，不写 D1 结构；F-3 残留队列会在下次同步被正常消费 |
| 发布风险 | ① 前后端版本错配窗口：Pages 先上、Worker 未上时，前端仍按旧 `400` 处理，功能表现是「照旧坏」而非新坏，可接受；② 已打开的旧标签页继续跑旧 JS，刷新后才生效（无强制刷新机制）；③ F-2 的重复累加不在本批解决，发布说明里不能说「排行榜已可信」 |

### 建议 2｜安全批（B-1 同步码限流、B-2 后台登录限流、B-3 AI 无限流）

| 项 | 评估 |
| --- | --- |
| 发布方式 | 全部 `wrangler deploy`（纯 Worker），**当前被 wrangler 凭证阻塞** |
| 影响面 | 全部 `/api/*`：`/api/bind`、`/api/admin/login`、`/api/ai/explain` 三个入口；B-3 若要求前端带 `deviceId`，还需同批发 Pages |
| 回滚成本 | **低-中**：`wrangler rollback` 到上一版本或重发旧提交；无 schema 变更。但限流状态全在内存 Map，回滚/重启即清零，无需迁移状态 |
| 停机 | 否（Worker 原子切换） |
| 数据迁移 | **否** |
| 发布风险 | ① **B-3 有破坏性**：后端一旦强制校验 `deviceId`，未刷新页面的旧前端（`js/aiExplain.js:653` 未带该字段）AI 解析立即全挂。必须「先发前端带 deviceId → 观察 → 再发后端强制」，或后端设宽限期（缺 deviceId 时降级为现有行为）；② B-1/B-2 用内存 Map 限流只能做到单 isolate 近似，跨 colo 不平滑，不要把「零限流」宣传成「已加固」；③ B-2 改按 `CF-Connecting-IP` 后，同 NAT 下的正常用户会共享配额，需确认阈值（现 8 次/15 分钟）不会误伤学校机房场景 |

### 建议 3｜地基批（迁移基线 0001 + 0003 可重放 + API base 环境覆盖）

| 项 | 评估 |
| --- | --- |
| 发布方式 | 三段：① `worker/migrations/` 补 0001 + 修 0003（纯仓库变更）；② 对生产 D1 执行 `wrangler d1 migrations apply ks-leaderboard --remote`（**生产 DDL**）；③ `js/api.js:15` + `js/logCollector.js:244/375/417` 的 BASE_URL 改环境变量（Pages 构建期注入） |
| 影响面 | D1 结构与迁移状态表；前端全部 API 调用；本地 dev 默认行为 |
| 回滚成本 | **高**：迁移无 unapply，回滚只能写反向迁移（`ALTER TABLE ... DROP COLUMN`，SQLite/D1 支持但**列内数据一并丢失**）；Pages 部分回滚低 |
| 停机 | 否（D1 迁移期间 Worker 继续服务，DDL 短暂锁表，本项目量级可忽略） |
| 数据迁移 | **是（最高风险项）**。已存在的生产库要知道「哪些迁移已执行」：0002/0004 都是 `IF NOT EXISTS` 可重放，**只有 0003（`ALTER TABLE users ADD COLUMN bookmarks`）在列已存在时必挂**（`schema.sql:9` 已有该列）。生产库若是手工执行 `schema.sql` 建的，`d1_migrations` 表为空，`apply` 会从 0002 起跑并在 0003 中断，0004 与后续 0005 全部卡住 |
| 发布风险 | ① **迁移前必须 `wrangler d1 export ks-leaderboard --remote --output=.tmp-release/ks-<date>.sql` 备份**，否则无退路；② 若生产已手工建列，需先 `INSERT INTO d1_migrations(name, applied_at) VALUES('0003_add_bookmarks.sql', ...)` 把已执行状态补齐（这是生产写操作，必须与 ks 确认后执行）；③ API base 环境变量的 Pages 项目配置若填错，**生产前端会指向错误域名导致全站 API 失效**——必须保留默认值兜底为 `https://ks-api.mutx.ccwu.cc`，且部署后实测一次首页 Network 域名；④ 本批是 B-5 编号项，也是第 5 批的硬前置 |

| 项 | 评估 |

| 项 | 评估 |
| --- | --- |
| 发布方式 | 三段且强耦合：① D1 迁移 0005（`stats.last_round_id`）→ ② `wrangler deploy` Worker（`/api/sync` 读 roundId）→ ③ Pages 前端传 UUID；①被 0003 阻塞（见建议 3），②被凭证阻塞 |

## 3. 发布前置条件（建议写进路线图「需要用户决策」）

1. **恢复 Cloudflare 凭证**：`wrangler login`（交互终端）或提供 `CLOUDFLARE_API_TOKEN`。否则第 2/3/5 批只能进仓库、不能上线。
2. **D1 备份机制**：目前仓库内无备份产物、无备份脚本。建议在第一次迁移前补一条 `wrangler d1 export --remote` 流程（可作为迁移批的第一个动作）。
3. **发布顺序约定**：`迁移 → Worker → 前端`；涉及契约变更时前端先行或后端宽限。
4. **发布检查单**：`git status` 干净 → 本地 `npm run lint` + `npm run build` EXIT=0 → `git push origin main` → 等 Pages 部署完成 → 冒烟（首页、`/api/banks`、`/api/leaderboard`、管理后台登录）→ 记录 commit 与部署时间。CI 绿不能替代本地门禁。

## 5. 路线图 R0–R5 逐条填充文本（可直贴 `docs/roadmap-2026-11-14.md`）

> 口径：发布通道 / 是否含不可逆迁移 / 回滚步骤与耗时 / 停机·迁移标记。
> 全局前提：Worker 侧发布当前被 `wrangler whoami` 的 `auth token has expired` 阻塞；前端 Pages 由 GitHub 集成自动部署，不需本地凭证。

### R1 · 止血批（F-5 / F-1 / F-3 clamp）

- **发布**：前端 `js/` 改走 Pages 自动部署（push `main` → 约 1–2 分钟）；F-3 的 3 行 clamp（`index.js:765-767`）走 `wrangler deploy`。
- **不可逆迁移**：无。
- **回滚**：前端——Pages 控制台回滚到上一部署或 `git revert` + push，约 2 分钟；后端——`wrangler rollback`，约 1 分钟。
- **停机**：否（Worker 原子切换）。**数据迁移**：否。
- **发布风险**：① clamp 上线后，`syncQueue` 里长期残留、且已按 `syncQueue.js:59-64` 累加放大的条目会在下一次同步**一次性成功提交**，相关用户排行榜数值会跳升——这是修复的预期副作用，发布说明里必须点明，否则会被当成新 bug；② 旧标签页继续跑旧 JS，刷新才生效；③ F-2 不在本批，不要把「排行榜已可信」写进发布说明。

### R2 · 安全批（B-1 / B-2 / B-3）

- **发布**：纯 Worker `wrangler deploy`；**仅当** B-3 选择「强制 deviceId」方案时，需同批发 Pages（`js/aiExplain.js:653`）。
- **不可逆迁移**：无。
- **回滚**：`wrangler rollback` 到上一版本，约 1 分钟；限流计数在内存 Map，回滚即清零，无状态迁移。
- **停机**：否。**数据迁移**：否。
- **发布风险**：① **B-3 是破坏性契约变更**：后端一旦强制 deviceId，未刷新的旧前端 AI 解析立即全挂。必须「Pages 先带 deviceId → 观察 1–2 天 → 再发 Worker 强制」，或后端设缺字段宽限期；② B-2 改按 `CF-Connecting-IP` 后，同 NAT/校园网用户共享配额（现 8 次/15 分钟），需评估误伤；③ 内存 Map 限流只做到单 isolate 近似，跨 colo 不平滑，别对外称「已加固」。

### R3 · 地基批（0001/0003 + API base 环境开关）

- **发布**：三段——① 仓库侧 `worker/migrations/` 补 0001、改 0003 为幂等；② **生产 DDL**：`wrangler d1 migrations apply ks-leaderboard --remote`（需凭证）；③ `js/api.js:15` + `js/logCollector.js:244/375/417` 改环境变量，Pages 构建期注入。
- **不可逆迁移**：**是（本路线图第一处）**。D1 迁移无 unapply，只能反向 write-down 迁移。
- **回滚**：① 迁移——`ALTER TABLE ... DROP COLUMN` 反向迁移（列内数据一并丢失），或从迁移前 `wrangler d1 export` 恢复（**恢复会丢掉导出点之后的所有写入**），约 1–2 小时；② Worker——`wrangler rollback`，1 分钟；③ Pages——回滚上一部署，2 分钟。
- **停机**：否（DDL 短暂锁表，本项目量级可忽略）。**数据迁移**：是。
- **发布风险**（2026-11-14 14:15 生产只读 PRAGMA 修正后）：① **迁移前必须** `wrangler d1 export ks-leaderboard --remote --output=.tmp-release/ks-2026-11-14.sql`，否则无退路；② 生产 `d1_migrations` **已存在且已记录 0002/0003/0004**（见第 9 节），原先「表为空、apply 会在 0003 中断」的假设不成立；**新的真实风险变成反向的**：仓库一旦补上 `0001_init.sql`，`apply --remote` 会把它当作未应用迁移执行，在已有库上 `CREATE TABLE` 会报 `table already exists`——因此 0001 基线**必须写成幂等**（全部 `IF NOT EXISTS`），或先在 `d1_migrations` 手工登记 0001（生产写，需 ks 确认）；③ `VITE_API_BASE` 若在 Pages 项目配置里填错，生产前端会指向错误域名导致全站 API 失效，**必须保留生产域默认值兜底**，部署后实测首页 Network 域名；④ 本批是 R5 的硬前置。

### R4 · 题库一致性批（12 题 / 23 答案 / 10 解析 / 备份）

- **发布**：**不经 git/CI**，走 `admin.html` 后台导入接口（`index.js:1982-2093`）与题目编辑接口直接写生产 D1；`electromechanical` 补备份是仓库新增 `banks/*.json`（随 Pages 构建，用户不可见）。
- **不可逆迁移**：无结构迁移，但**生产数据写**，且导入链路只增不减 → 实质不可逆。
- **回滚**：**没有后台撤回路径**。`index.js:1997/2015` 追加 `id = maxId + added + 1`；`bank_history` 只写 `detail`，`snapshot` 死字段从未写入 → 题量只能靠导入前导出的 `questions_json` 快照整库覆盖（需 D1 SQL 或再造导入入口）或直接 `DELETE`，约 30 分钟+ 且需人工核对。内容修改（答案/解析）覆盖即丢旧值，同样无快照。
- **停机**：否，但需**低峰窗口**（`2074-2078` 是整库 `questions_json` 覆盖）。**数据迁移**：是（内容数据）。
- **发布风险**：① 导入前先导出该库 `questions_json`（或确认 `banks/fixture-design-ch2.json` 与线上 75 题一致）作为唯一还原源；② 重复导入会产生重复题；③ `img` 字段导入链路本轮未验证，必须先本地 admin 导入 id 76–87 验证渲染；④ 12 题为 id 76–87 追加，不重排，用户端按 id 索引的 localStorage 进度不受影响。

### R5 · 数据可信度批（roundId + F-2 + 脏数据）

- **发布**：强顺序三段——① 迁移 `0005_add_last_round_id.sql`；② `wrangler deploy`；③ Pages 前端传 UUID。①依赖 R3，①②依赖凭证。
- **不可逆迁移**：**是**（加列 + 存量脏数据的一次性校正）。
- **回滚**：代码 `wrangler rollback` 可退；`last_round_id` 列留着对老客户端无害（不传则行为不变）；但**已写入的累加数据不会随代码回滚**；人工校正 = 生产 `UPDATE`，不可逆，必须先导出 `stats`/`users`。
- **停机**：否；校正时刻排行榜数值会跳变，建议低峰并公告。**数据迁移**：是。
- **发布风险**：① 顺序错了不报错但不生效（前端先传 `roundId`、Worker 未识别 → 忽略），安全但会误以为已修好；② 老客户端不传 `roundId` 必须保持累加语义，**不能改成覆盖**，否则跨设备统计被打回；③ 脏数据无权威真值，任何修正都要留导出与变更记录。

### R0 · 条件项（生产 `users.bookmarks` 缺列时）

## 8. 本机网络注意事项（wrangler 必读，2026-11-14 实测）

**`dash.cloudflare.com` 在本机 IPv4 全部超时、IPv6 正常。** Node 的默认 DNS 结果是 IPv4 优先，因此 `wrangler login` 在拿到授权码后做 token 交换时会直接 `fetch failed`，表现为「登录莫名失败」，与授权无关。

实测：

| 目标 | IPv4 | IPv6 |
| --- | --- | --- |
| `https://dash.cloudflare.com/` | 超时（`curl -4` 12s，000） | 通（`curl -6` 返回 403，属正常 WAF 拦截静态请求） |

**结论：本机所有 wrangler 命令前必须加**

$env:NODE_OPTIONS='--dns-result-order=ipv6first'
