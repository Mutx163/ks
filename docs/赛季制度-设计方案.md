## 2. 表结构

### 2.1 赛季表（新增）

```sql
CREATE TABLE IF NOT EXISTS seasons (
    id         TEXT PRIMARY KEY,        -- 稳定标识，如 legacy / 2026-fall
    name       TEXT NOT NULL,           -- 展示名，如「2026 秋季学期」
    start_date TEXT,                    -- 可空，仅展示，不参与判定
    end_date   TEXT,                    -- 可空，同上
    is_active  INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL
);

-- 只能有一个当前赛季（部分唯一索引，SQLite/D1 支持）
CREATE UNIQUE INDEX IF NOT EXISTS idx_seasons_active
    ON seasons (is_active) WHERE is_active = 1;
```

`is_active` 用**部分唯一索引**而不是 CHECK 约束，是因为 CHECK 无法表达“全表至多一行”。切换赛季时先 `UPDATE seasons SET is_active = 0`，再设目标为 1，两步放在同一个 `db.batch`（D1 批内事务）里，避免瞬间出现两个 active。

### 2.2 stats 如何关联赛季：两案对比

**案 A（推荐）：重建 `stats`，主键加 `season_id`**

```sql
CREATE TABLE stats_new (
    user_id    TEXT NOT NULL,
    bank_id    TEXT NOT NULL,
    season_id  TEXT NOT NULL,
    bank_name  TEXT DEFAULT '',
    answered   INTEGER DEFAULT 0,
    correct    INTEGER DEFAULT 0,
    duration   INTEGER DEFAULT 0,
    updated_at TEXT NOT NULL,
    PRIMARY KEY (user_id, bank_id, season_id),
    FOREIGN KEY (user_id) REFERENCES users(id)
);
INSERT INTO stats_new (user_id, bank_id, season_id, bank_name, answered, correct, duration, updated_at)
    SELECT user_id, bank_id, 'legacy', bank_name, answered, correct, duration, updated_at FROM stats;
DROP TABLE stats;
ALTER TABLE stats_new RENAME TO stats;
CREATE INDEX IF NOT EXISTS idx_stats_season_answered ON stats (season_id, answered DESC);
CREATE INDEX IF NOT EXISTS idx_stats_season_updated  ON stats (season_id, updated_at);
```

- **为什么必须重建**：现有主键是 `(user_id, bank_id)`，只加列不加主键的话，同一用户同一题库跨赛季只有一行，新赛季第一笔同步会把旧赛季的数字累加上去——赛季就形同虚设。
- 影响面：13 处读加 `AND s.season_id = ?`，3 处写多带一个 `season_id` 参数；历史数据全归 `legacy`，同一张表可查。
- 回滚：**不需要反向迁移**——保留 `season_id` 列、查询去掉过滤条件即可退回“单赛季视图”，数据一行不丢。
- 风险：重建是 4 条语句的批量替换，78 行数据（生产实测），瞬时完成；`stats` 是子表（被 `users` 引用的是它自己），DROP/RENAME 不会破坏别的表的 FK。

**案 B（不推荐）：新建 `season_stats`，把 `stats` 冻结为历史表**

- 优点：不动现有表；回滚 = DROP 新表。
- 致命缺点：**每个读路径都要按赛季选表**——查当前赛季读新表、查历史读旧表，后台的跨赛季聚合还要 UNION 两张 schema 不同的表。18 个读写点会变成 30+ 个分支，且新表与旧表结构不一致，以后每次改动都要同步两份。
- 只在“完全不能动现有表”时才选它；本项目 78 行、无外键依赖压力，没有这个必要。

**推荐：案 A。**

## 3. 迁移方案（本批只写，不执行）

### 3.1 为什么拆成 0006 + 0007

SQLite 没有 `ADD COLUMN IF NOT EXISTS`，也不能在纯 SQL 里做条件分支（我们在 0003 已经验证过）。`0007` 是**表重建**，重放一次就会把 `stats` 再拆一遍、数据全丢。所以：

- `0006_seasons.sql`：建表 + 唯一索引 + 种子赛季，**全部天然幂等**，可反复执行。
- `0007_stats_season.sql`：表重建，**由 `scripts/apply-migrations.ps1` 先用 `PRAGMA table_info(stats)` 检查 `season_id` 是否存在**，存在就 `[skip]`。和 0003 用的是同一套运行器守卫。

生产 `d1_migrations` 已有 0001–0005，所以序号从 0006 起；0007 顺延（不是 0006 一文件装两步，理由如上）。

### 3.2 执行顺序（每步后跟只读校验）

**Step 1 — `0006_seasons.sql`**

```sql
CREATE TABLE IF NOT EXISTS seasons (
    id TEXT PRIMARY KEY, name TEXT NOT NULL, start_date TEXT, end_date TEXT,
    is_active INTEGER NOT NULL DEFAULT 0, created_at TEXT NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_seasons_active ON seasons (is_active) WHERE is_active = 1;

-- 历史赛季（现有全部数据归属）
INSERT OR IGNORE INTO seasons (id, name, start_date, end_date, is_active, created_at)
VALUES ('legacy', '历史数据（赛季制度上线前）', NULL, NULL, 0, datetime('now'));

-- 初始当前赛季：只在没有任何 active 赛季时插入（纯 SQL 条件插入，幂等）
INSERT INTO seasons (id, name, start_date, end_date, is_active, created_at)
SELECT 'season-initial', '当前赛季（待管理员改名）', NULL, NULL, 1, datetime('now')
WHERE NOT EXISTS (SELECT 1 FROM seasons WHERE is_active = 1);
```

校验（只读）：
```sql
SELECT id, name, is_active FROM seasons ORDER BY id;
-- 期望：legacy(0) + 一个 is_active=1
SELECT COUNT(*) FROM seasons WHERE is_active = 1;   -- 期望 1
```

**Step 2 — `0007_stats_season.sql`**（内容即 2.2 案 A 的 6 条语句）

校验（只读）：
```sql
PRAGMA table_info(stats);                                  -- 期望 9 列，含 season_id
SELECT COUNT(*) FROM stats;                                -- 期望 = 迁移前行数（生产 78）
SELECT COUNT(*) FROM stats WHERE season_id IS NULL;        -- 期望 0
SELECT season_id, COUNT(*) FROM stats GROUP BY season_id;  -- 期望只有 legacy
```

**Step 3 — 管理员建新赛季并激活**（走 API，不是迁移）

```sql
-- 等价操作，供核对
UPDATE seasons SET is_active = 0 WHERE is_active = 1;
UPDATE seasons SET is_active = 1 WHERE id = '2026-fall';
```

校验：`SELECT id,name,is_active FROM seasons WHERE is_active=1;` → 期望恰好一行。

## 4. API 变更

### 4.1 读：`GET /api/leaderboard`

- 新增可选参数 `season`：
  - 不传 / `active` → 当前赛季（**老客户端行为不变**）
  - `legacy` → 历史赛季
  - 具体 id → 该赛季
- 未知 id → `404 {"error":"赛季不存在"}`；不存在的季度不静默回落到 active（避免“以为在看历史、其实在看现在”）。
- 响应新增 `season: { id, name }`；`statsData` 的今日活跃/总活跃也按该赛季过滤（否则新赛季第一天会显示历史活跃数）。
- `sort` / `limit` / `stats=1` / `deviceId` 语义全部不变。

### 4.2 写：`/api/sync`、`/api/bind`、admin 调整

- **赛季 id 由服务端解析，绝不接受客户端传**（可伪造，能把数据写进任意赛季）。
- `resolveActiveSeason(env)`：`SELECT id FROM seasons WHERE is_active = 1`，单请求内复用一次结果。
- 三个 upsert 的 `ON CONFLICT` 目标改为 `(user_id, bank_id, season_id)`。
- **没有 active 赛季时的兜底**：取 `created_at` 最大的赛季写入，并 `console.error` 记录。不选择“直接报错”——那会让所有老客户端同步失败。
- 老客户端请求体完全不变（不带 season），所以兼容。

### 4.3 新增管理端点（设计稿）

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/admin/seasons` | 列表 + 每季题数统计 |

## 5. 兼容与风险

1. **老客户端零改动**：所有新参数可选，默认 active。
2. **切换瞬间的写请求**：按服务器处理时刻的 active 赛季落库；切换前发出、切换后到达的请求会落进新赛季（最多一个请求的量）。可接受，但要在发布说明写一句。
3. **本地失败队列（SyncQueue）跨赛季**：用户积压的增量在切换后重发，会记到**新赛季**。这是“赛季分桶 + 客户端队列”的固有现象，不能靠客户端上报赛季修正（可伪造）。接受，记录在案。
4. **78 行 stats 重建**：单迁移内完成，无并发写；`bank_id` 无 FK，删题库的清理逻辑（2139）要同步加 season 条件吗？——不需要，删题库应清掉**所有赛季**的该库数据，保持现状即可。
5. **索引**：新增两条 `(season_id, ...)` 索引；旧索引 `idx_stats_answered` / `idx_stats_duration` 可保留（排行榜将变成 `WHERE season_id=? ORDER BY answered`，新索引会接管），本批不删旧索引，避免无关变更。
6. **排行榜口径**：同一用户跨赛季的排名互不影响；`currentUser.rank` 的“恒按答题数”老问题（体检 B-8）依旧存在，不在本批修。

## 6. 回滚

| 层级 | 动作 | 数据影响 |
|---|---|---|
| 首选（轻） | 代码回退到“忽略 season_id 过滤”的查询版本，`stats` 里 `season_id` 保留不用 | **零丢失**，等价单赛季视图 |
| 彻底（重） | 新增迁移把 `stats` 重建回无 `season_id` 的结构 | 需先用 `d1 export` 快照，逐步可逆 |
| 赛季本身 | 把 `is_active` 指回 `legacy` 即恢复旧榜 | 零丢失 |

**结论：赛季方案不需要“反向迁移”也能软回退**，这是选案 A 而不是改主键外新建表的主要收益之一。

### 8.4 失败止损（0007 中途失败）

`DROP TABLE stats` 成功但 `RENAME` 失败时，数据在 `stats_season_new` 里没丢：

```sql
-- 先查这两张表谁在
SELECT name FROM sqlite_master WHERE type='table' AND name IN ('stats','stats_season_new');
-- 情况 A：stats 不在、stats_season_new 在 → 直接补 RENAME，数据完整
ALTER TABLE stats_season_new RENAME TO stats;
-- 情况 B：两张都在（说明 DROP 之前就失败）→ 删掉半成品，看 d1_migrations 里 0007 是否已记录，再决定重跑
DROP TABLE IF EXISTS stats_season_new;
```
两种情况都**不要**直接重跑 0007，先按上面查清状态；必要时从 8.1 的 dump 恢复。

### 8.5 部署顺序（关键风险）

**必须先迁移（0006/0007），再部署 Worker。** 原因两条：

1. **代码依赖新列**：新版查询硬引用 `season_id`，若先部署、后迁移，`/api/leaderboard`、`/api/sync` 会全部 `no such column: season_id` → 500。
2. **反过来也有窗口**：迁移完成、新代码未上线时，旧代码的 `/api/sync` 用的是 `ON CONFLICT(user_id, bank_id)`，而唯一约束已变成三列 → SQLite 报 `ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint`，同步会短暂 500。

**因此 0007 与 Worker 部署必须紧邻执行**（低峰、1–2 分钟内）。窗口内用户同步失败不会丢数据——前端 `SyncQueue` 会把增量入队，稍后重试成功。发布说明要写这一条。
