### 8.5 本地 IP 模拟与线上语义差异（必须写进结论）

- 本地 miniflare 请求**没有** `CF-Connecting-IP`；`getClientIp()` 回退到 `X-Forwarded-For`，测试脚本因此注入 `203.0.113.x` 模拟客户端 IP。
- 线上 Cloudflare 由边缘**强制注入** `CF-Connecting-IP`，客户端无法伪造 `X-Forwarded-For` 覆盖它（且 `getClientIp` 优先读 CF 头）。
- 所以：**本地 429 证明的是「限流逻辑/阈值/顺序正确」，不能证明线上阈值表现一致**（例如 NAT 后真实用户共享同一出口 IP 的聚合效应、IPv6 地址分布、多 isolate 内存计数不共享，本地都测不出）。
- 同理，本地浏览器页面请求不带任何 IP 头，B-2/B-3 的 IP 维度在页面上是空键——这两个限流项**只能用带 `X-Forwarded-For` 的 HTTP 脚本验**，UI 端只能验 B-1（deviceId 维度）与 429 文案。

### 10.1 B1 线上：**429 已复现**，且正确码放行

设备：全新 `t-r2-final-202649`（非历史测试设备），无人工延时，`curl --max-time 10`、不重试。

```
第 1 段（11 次）：404,000,000,404,404,000,404,404,404,404,404
续打：            000,000,404,429  ← 429 at cumulative attempt #15
```

- 其中 `000` **不是请求没到**：请求已经到达并计入了失败次数，只是出口走的是 IPv6 链路（`2408:8463:…`），响应没有回来。证据：清理时表里 `bind:ip:2408:8463:5b10:29dd:f91b:5b7c:5727:e2d7` 的 `count=10`，正好对应那批无响应的请求；
- **429 响应体**：`{"ok":false,"error":"同步码尝试过于频繁，请 15 分钟后再试","retryAfterSeconds":780,"retryAfter":780}`；响应头 `Retry-After: 780`；
- **紧接着正确码 `7Y4C7C`** → **200 `{"ok":true,"alreadyBound":true}`** —— ks 加的关键判据通过：**限流期内正确码仍放行**，用户手滑后仍能进去。

**本条是本批唯一「既防了爆破、又没误伤用户」的证明**：429 拦住了猜错，但正确码不被拦。后续改动限流逻辑时，这条必须一起回归。

结论：**B1 线上 PASS**（D1 持久计数生效；此前内存版的「38 次全 404」不再复现）。

### 10.2 测试桶（正确名字，已由发布官清理）

- **设备桶前缀是 `bind:dev:`**（不是 `bind:device:`）：`bind:dev:t-r2-final-202649`，清理时 `count=11`
- **出口 IP 是 IPv6**：`bind:ip:2408:8463:5b10:29dd:f91b:5b7c:5727:e2d7`，清理时 `count=10`
- `198.200.42.69` 是 IPv4 链路的探测结果，**在限流表里根本不存在**；本机到 Cloudflare 实际走 IPv6（这也是 `wrangler` 必须加 `NODE_OPTIONS=--dns-result-order=ipv6first`、以及本轮那些 `000` 的原因）

> 发布官已执行 `DELETE … WHERE bucket IN ('bind:dev:t-r2-final-202649','bind:ip:2408:8463:…')`（`rows_written: 2`）。表里另一行 `bind:ip:123.147.245.237, count=1` 是真实用户输错同步码留下的记录，**按裁定保留**，15 分钟后自然过期。

### 10.2.1 两条比 PASS 本身更重要的结论

1. **429 出现在累计第 15 次，不是第 11 次**；设备桶 `count=11`、IP 桶 `count=10`，两个数还不一致 —— 说明同一轮请求被分散计数。所以「允许 N 次、第 N+1 次 429」**只是语义，不是精确常量**，阈值附近行为会抖，以后**不要拿具体次数当断言**。
2. **正确码在限流期内仍 200**（`alreadyBound`），这是唯一的「防爆破且不误伤用户」证据，回归时必须一起验。
